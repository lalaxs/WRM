# Stage 4 NPC World, Relationships, Events, Sects, and World UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use `superpowers:subagent-driven-development` for implementation and `superpowers:requesting-code-review` after every task. Every task below is sequential. Do not run two implementers against runtime files at the same time.

**Goal:** Deliver a deterministic, permanently saved UI-driven character world: randomly generated NPCs, active/background simulation tiers, directional relationships and charm-driven social actions, non-expiring decision events and named parallel social progress, selectable/evolving sects, abstract regions, and complete `事件 / 宗门 / 天下 / 关系` pages inside the existing UI skeleton.

**Architecture:** Stage 4 extends the Stage 1B pure `Simulation.advance` boundary and the verified Stage 2/3 model. Static regions, sect identities, NPC generation tables, social interactions, and authored event templates live in `content/`. Pure NPC, relationship, event, sect, and social rules live in `core/`. `core/stage4-rules.js` adapts those modules to the existing event-boundary simulation; it does not create a second timer. The UI reads frozen ViewModels and sends commands through the frozen `GameAPI`.

**Tech Stack:** Native JavaScript, UMD browser globals plus CommonJS exports for Node self-tests, existing HTML/CSS/Canvas/DOM runtime, no package dependency, no framework, no server, no generated text service.

## 0. Start Gate and Canonical Decisions

Do not begin Task 1 until:

1. Stage 1B, Stage 2, and Stage 3 completion gates pass from a clean checkout.
2. `npm test` includes their focused suites.
3. Stage 3 has published its final save schema, action descriptor, report extension, and `GameAPI` method list.
4. Root source is authoritative and `release/` is still generated by the verified sync script.

The expected migration chain is:

```text
schema v1  legacy normalized snapshot
schema v2  Stage 1B simulation model
schema v3  Stage 2 life skills / inventory / homestead
schema v4  Stage 3 combat / techniques / breakthroughs
schema v5  Stage 4 NPC / relationship / event / sect world
```

If Stage 3 lands with a version other than v4, change only the Stage 4 constants and migration test fixtures so Stage 4 is exactly `previous + 1`. Never skip a version and never make a v5 normalizer silently accept an unknown future version.

The current Stage 3 plan reserves `player.techniques`, `player.combat`, `player.combatProgress`, `player.breakthrough`, and `systems.combat`, and extends the existing parallel lane for injury recovery. Stage 4 preserves those fields and its combat/technique/breakthrough query and command methods unchanged. Social technique-understanding rewards go through the Stage 3 adapter; Stage 4 must not write Stage 3 technique internals directly.

The only authoritative product source is:

`docs/superpowers/specs/2026-07-24-xiuxian-idle-core-design.md`

Locked product decisions:

- There is no large map, grid, free movement, map exploration, or map renderer.
- World presence is expressed through permanent character records, abstract region labels, sect state, lists, cards, event text, and summaries.
- The existing fixed top bar, scrollable left navigation, independently scrollable right content area, modal layer, CSS direction, and player-avatar composition remain.
- The player identity is female. NPC gender never restricts friendship, romance, or partnership.
- User-facing copy says `人物`, a person's name, or a concrete action. It must not expose blunt text such as `NPC响应`, `等待NPC`, `系统等待`, or `双修`.
- Use `与某人一起修炼`.
- Charm has level and XP only. There is no charm mastery or proficiency record.
- Active social actions occupy the one main action slot. Event-created named social progress uses the uncapped parallel lane and never replaces the main action.
- Relationship values are directional and visible. Relationship stage is changed only by a resolved authored event, never because a number crossed a threshold.
- Pending player decisions never expire and are never overwritten.
- At 20 pending decisions, new player-involved key events pause. Autonomous character and sect simulation continues and is summarized.
- Offline world, sect, age, and parallel-social time uses full real elapsed time; it is not capped by the main-action offline cap.
- Every random decision consumes serialized RNG state through an injected deterministic random source. No Stage 4 runtime file may call `Math.random()`.
- No online text generation is used. Events are deterministic rules plus authored templates and saved variable substitution.

### Scope boundary

Stage 4 implements NPC cultivation/breakthrough, travel, sect membership changes, relationship creation/conflict, romance/partnership/breakup event transitions, sect evolution, and age advancement.

Stage 5 owns playable descendants, childbirth depth, death resolution, reincarnation, ascension, lineage, inheritance, and the inheritance hall. Stage 4 must include durable fields and event categories for those later systems, but must not fake those outcomes.

Rules:

- NPC IDs are the stable identity. Display names are not keys and need not be globally unique.
- `player.regionId` is an abstract location condition/filter only. It never becomes coordinates or a movable map avatar.
- NPC records are never removed. Later lifecycle systems change `status`; they do not delete the record.
- Sect membership has one source of truth: `npc.sectId` for NPCs and `systems.sects.player.sectId` for the player. Sect records must not duplicate a mutable `memberIds` array.
- Relationship edges are sparse and keyed as `sourceId>targetId`.
- Bond keys are unordered: sort the two IDs lexicographically and join with `|`.
- All eight values are finite integers clamped to `0..100`. Resentment represents hostility; positive dimensions are not encoded as negative numbers.
- `pending` has a hard capacity of 20. It is never compacted.
- `summaries` keeps the most recent 300 detailed records and `evolution` the most recent 500. Older records are merged into immutable monthly/30-day aggregate entries in `compacted`; do not silently discard counts or important IDs.
- Stage 1B `reportArchive` remains the single source for acknowledged offline/action settlement reports. `systems.events.summaries` stores person/sect/parallel summaries only; `queries.events({section:'summary'})` merges frozen rows from both sources without duplicating the report into a second persisted array.
- A completed social parallel job that cannot create its follow-up because pending is full remains in `jobs` with `ready:true`. It is promoted after capacity opens. It is reported complete only once.

### 1.2 NPC simulation cadence

Use fixed event boundaries:

```js
ACTIVE_STEP_SECONDS = 15 * 60;
BACKGROUND_STEP_SECONDS = 6 * 60 * 60;
SECT_STEP_SECONDS = 24 * 60 * 60;
EVENT_SLOT_SECONDS = 2 * 60 * 60;
WORLD_DAY_SECONDS = 24 * 60 * 60;
```

- Active target is 40 and is clamped to the canonical 30–50 range.
- Active characters receive detailed 15-minute decisions.
- Background characters are processed in deterministic six-hour batches.
- Sect evolution resolves once per world day.
- Key player event budget is deterministically rolled once per world day as an integer from 5 through 10.
- Event attempts are spread across two-hour slots. When capacity permits and an eligible template exists, the seeded first world must produce its rolled daily budget.
- The engine must process exact boundaries so one 48-hour advance and 192 fifteen-minute advances end with byte-equivalent normalized state.

### 1.3 Relationship and social contracts

The eight exact relationship keys are:

```js
[
  'affection',
  'trust',
  'romanticAttachment',
  'desire',
  'dependence',
  'loyalty',
  'jealousy',
  'resentment'
]
```

The shared Stage 2 charm formulas remain authoritative:

```js
positiveRelationMultiplier(level) {
  return Math.min(1.49, 1 + (level - 1) * 0.005);
}

misunderstandingReduction(level) {
  return Math.min(0.30, (level - 1) * 0.003);
}
```

`SkillProgression.gainCharmXp` must still reject any source other than `{source:'social'}`. No code creates `player.mastery.charm`.

Main-slot social action keys use:

```text
social:<interactionId>:<npcId>
social:gift:<npcId>:<itemId>
```

All social actions are finite, count 1. The first batch has these exact shared interactions:

| ID | Label | Base duration |
|---|---|---:|
| `talk` | 交谈 | 120s |
| `gift` | 赠礼 | 60s |
| `accompany` | 陪伴 | 300s |
| `discussDao` | 论道 | 480s |
| `outing` | 出游 | 900s |
| `visit` | 拜访 | 600s |
| `cultivateTogether` | 与某人一起修炼 | 1200s |

Each completion:

1. grants charm XP with `source:'social'`;
2. applies saved-RNG personality-adjusted directional deltas;
3. applies Stage 2 charm multiplier only to positive player-to-person deltas;
4. applies misunderstanding reduction to the authored base misunderstanding chance;
5. grants the interaction's declared cultivation, skill XP, resource, technique-understanding, or temporary benefit;
6. may unlock an event, but never changes a bond stage directly.

`Relationships.canRomance(model, firstId, secondId)` returns false for blood relatives, direct in-laws, guardianship links, and a prior generation's formal partner. Gender is never part of the rejection logic.

### 1.4 Saved event instance and template DSL

Templates are frozen, data-only objects. Do not use `eval`, serialized functions, or arbitrary property paths.

```js
{
  id: 'social-rain-shelter',
  revision: 1,
  category: 'social',
  scope: 'player',
  weight: 10,
  participants: { min: 1, max: 1 },
  requirements: [
    { type: 'npcStatus', value: 'living' },
    { type: 'relationAtLeast', metric: 'trust', value: 5 },
    { type: 'sameRegion' }
  ],
  title: '檐下听雨',
  text: '{npcName}邀你在{regionName}暂避一场急雨。',
  options: [
    {
      id: 'stay',
      label: '留下听雨',
      preview: '这需要一些时间',
      effects: [
        { type: 'relationDelta', direction: 'both', values: { trust: 2 } },
        {
          type: 'queueParallel',
          label: '与{npcName}檐下听雨',
          durationSeconds: 900,
          followupTemplateId: 'social-rain-shelter-result'
        }
      ]
    }
  ],
  cooldownSeconds: 86400
}
```

Allowed requirement types:

```text
npcStatus, personalityIn, valueProfileIn, romancePrincipleIn,
sameRegion, regionIn, playerSectIn, npcSectIn, realmAtLeast,
relationAtLeast, relationAtMost, bondStageIn, romanceEligible,
flagEquals, cooldownReady
```

Allowed effect types:

```text
relationDelta, setBondStage, setRomancePrinciple, addItem, addCultivation, addSkillXp,
addTechniqueUnderstanding, addTemporaryBenefit, sectJoin, sectLeave,
addSectContribution, addSectReputation, moveNpc, queueParallel,
queueFollowup, appendSummary
```

Unknown requirements/effects fail closed with a warning record. They must not partially resolve an event.

A pending event stores a complete rendered snapshot so it remains valid after content changes:

```js

      preview: '这需要一些时间',
      effects: []
    }
  ]

```

Save the validated effect snapshot inside each option. Resolving an old pending event must not depend on the current template revision.

### 1.5 Public API additions

Preserve all Stage 1B/2/3 methods and frozen boundaries. Add:

```js
queries.events({ section, filter, cursor })
// section: 'summary' | 'pending' | 'world'
// filter for world: 'nearby' | 'all'

queries.relationships({ search, sort })
// sort: 'recent' | 'affection' | 'trust' | 'name'

queries.relationship({ npcId })
queries.social({ npcId })

// scope: 'nearby' | 'all'

commands.chooseEvent({ eventId, optionId })
commands.markEventSectionRead({ section, ids })
```

Rules:

- All queries return deep-copied, deeply frozen ViewModels.
- All commands return the established `{ok,code,changed,message,data}` shape.
- `startSocial` delegates to the one main action slot and uses the existing single-slot switching semantics.
- `chooseEvent` is atomic. If costs fail, a same-person parallel job already exists, or an effect is invalid, the event stays pending and no partial state is committed.
- There is no public command to set relationship values/stages or directly force NPC/sect life decisions.
- Sect joining, leaving, and changing happens through event options handled by `chooseEvent`.

## 2. Required First Playable Content Batch

The first Stage 4 batch is production content, not placeholder cards:

- **120 permanent NPCs** on first bootstrap.
- **40 active / 80 background** after the first deterministic rebalance.
- **8 abstract regions:** 2 towns/cities, 1 market, 2 sect-base clusters, 2 wilderness areas, 1 special realm. They are labels and conditions only.
- **5 fixed sect identities** within the canonical 4–6 range:
  - `太玄剑宗`: combat, forging, direct personalities;
  - `百草谷`: herb gathering, alchemy, patient personalities;
  - `天工阁`: forging, formation, practical personalities;
  - `灵兽山`: beast taming, farming, forthright personalities;
  - `清音宫`: talisman, charm, diplomatic personalities.
- **NPC generation data:** at least 32 surnames, 48 given-name components, 18 appearance features, 12 personality profiles, 8 value profiles, 12 talents, and the 4 canonical romance principles.
- **16 generated family/household IDs** distributed across the bootstrap population. These are social data only; Stage 5 adds lineage behavior.
- **17 active interactions:** the 7 shared interactions plus 2 identity/sect-specific interactions for each of the 5 sects.
- **10 named parallel-progress patterns,** including `互寄书信`, `准备赴约`, `等待论道之日`, `打听某人的消息`, and `为对方寻找礼物`. Every rendered label contains the person's name or a concrete destination/activity.
- **40 authored event templates:**
  - 12 social encounter/follow-up templates;
  - 8 relationship, romance, partnership, conflict, or separation templates;
  - 8 sect choice/task/politics templates;
  - 6 region templates;
  - 6 world-person/sect evolution templates.

At least one first-batch event must exercise each of:

- a two-direction relationship delta;
- a bond stage transition decided by an event;
- an explain/compensate/negotiate/exit conflict option;
- a named parallel progress and follow-up;
- a sect join;
- a sect leave or change with contribution/reputation/relationship consequences;
- a nearby world summary;
- an all-world sect change.

The formal sect-choice event is queued only after the player's first completed main action. The player begins as `散修`. Its options are the five sects plus `继续以散修身份游历`; choosing the latter resolves the event and allows a new invitation after a one-day cooldown.
