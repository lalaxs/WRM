## 三、值得注意的问题（按严重度）

### 🔴 高

**H1. `game.js` 残留整套 Canvas UI 子系统（架构违规 / 技术债）**
- 现象：`game.js` 仍保留约 210 处 `ctx.fillText/fillRect` 手绘 UI，以及 `drawLeftNav / drawTopBar / drawGameContent / drawBreakModal / drawLunhui / drawCreator / drawInventory / drawToast` 等十余个 Canvas UI 函数，仅作为"ui.js 未加载时的兜底分支"存在。
- 偏差：设计意图是"UI 全 DOM、Canvas 只画角色立绘"。生产环境（index.html 同时加载 ui.js）兜底永不触发，这些全是已迁 DOM 未删的死代码，违反 `index.html` 注释约束与 Stage 6 的 UI 边界。
- 风险：维护隐患；若 ui.js 因异常未加载，会回退到过时/不一致的 Canvas 界面。
- 建议：确认 DOM UI 稳定后，删除 `render()` 兜底分支（约 game.js:3204-3217）及全部 `draw*` UI 函数，仅保留 `drawCharacter` 立绘合成。

**H2. 突破渡劫自动战斗未接，大境界突破走"概率判定占位"（需核查合规）**
- 现象：`game.js` 大境界突破用"概率判定占位"（约 :1356），并标记 `TODO` 接 §4 自动战斗渡劫（约 :1360）未接。
- 偏差：spec §260-270 要求突破有"通关副本/击败首领/完成宗门试炼"等**突破任务门槛**，门槛完成永久记录；且突破概率只允许"境界基础 + 丹药 + 事件增益"三来源（§273-279），功法/装备/阵法/灵兽/关系/洞府不得直接改概率。
- 待核查：该占位概率的来源是否满足"仅三来源"；突破任务门槛是否真正校验。属合规红线，建议优先核查。

### 🟠 中

**M1. 广告变现：权威文档与项目 memory「架构定稿」冲突（基准不一致）**
- 权威文档：spec §29 仅把"广告"点名为网络用途之一；**Stage 6 §337 明确"不在 Stage 6 发明 ad reward"**；全 stage 无 AdManager 设计任务。
- 项目 memory 架构定稿：曾定"H5 走 TapTap 开发者中心内置广告变现，集中封装 AdManager.js"。
- 实际：`platform.js` 无广告/登录 SDK 函数（仅注释占位），无 `AdManager.js`，index.html 的 TapTap SDK 引入被注释。
- 结论："广告缺失"在最新权威文档下属于"设计点名但未落地/延期"，**并非偏离**；但与你之前的架构定稿方向相左。**建议明确以哪份文档为准**，避免后续开发方向打架。

**M2. 双调色板（单一真相被破坏）**
- 现象：styles.css `:root`（主色 `#BBA8E8`、深紫 `#8B6FD4`）与 `game.js` 内部 `THEME`（primary `#D4C8ED`、primaryD `#9985CC`）值不一致；Canvas 兜底还散用硬编码 `rgba(74,64,99,…)` 等。
- 偏差：Stage 6 §16 要求"保留统一 CSS 类名与色调、单一真相"。生产走 DOM 用 `:root`，故不影响视觉，但违背单一来源原则。
- 建议：删除 Canvas 兜底后自然消解；或统一以 `:root` 为唯一调色板。

**M3. UI 双重实现（与 H1 同源）**
- 创建/突破/轮回/离线面板在 Canvas(game.js) 与 DOM(ui.js) 各实现一份。收敛方向同 H1。

**M4. 商城/商店未实现**
